# Инструкция для Codex: реализация Figma 1:1

## Цель

Реализуй интерфейс из переданной ссылки на Figma максимально близко к исходному дизайну **1:1** в существующем проекте.

Я передам тебе только:

1. эту инструкцию;
2. ссылку на Figma.

Все остальное определи самостоятельно по Figma, структуре проекта и доступным инструментам.

Не проси меня вручную указывать:

- viewport;
- route;
- размеры frame;
- список ассетов;
- шрифты;
- цвета;
- отступы;
- breakpoint'ы;
- названия компонентов;
- путь страницы;
- структуру layout;
- технические параметры, которые можно определить самостоятельно.

Работай автономно до максимально точного результата.

---

# 1. Главный принцип

**Figma — источник истины для визуального результата.**

Не делай просто похожий интерфейс.

Не интерпретируй дизайн по-своему.

Не упрощай дизайн без технической необходимости.

Не улучшай UI от себя.

Не меняй визуальные решения на более привычные или "правильные".

Если данные можно получить из Figma, проекта, браузера, файловой системы или доступных инструментов — получи их самостоятельно.

# 3. Самостоятельно определи целевой viewport

Я не буду сообщать viewport вручную.

Определи его самостоятельно.

Используй в первую очередь:

1. фактический размер целевого Figma frame;
2. размеры layout/grid;
3. constraints и Auto Layout;
4. соседние варианты того же экрана;
5. breakpoint-версии;
6. структуру проекта;
7. существующие responsive rules.

Если Figma содержит несколько версий экрана, самостоятельно пойми, какая из них соответствует целевой реализации.

Если имеются desktop / tablet / mobile варианты, реализуй responsive behavior настолько полно, насколько он однозначно следует из Figma.

Для визуальной проверки используй размер соответствующего Figma frame как основной reference viewport.

Не спрашивай меня, какой viewport использовать, если это можно определить из макета.

---

# 4. Самостоятельно определи route страницы

Я не буду сообщать route вручную.

Перед реализацией изучи проект и самостоятельно найди правильное место для страницы.

Проверь:

- router;
- routes config;
- app directory;
- pages directory;
- layouts;
- navigation;
- menu;
- ссылки;
- существующие страницы;
- названия feature-модулей;
- URL conventions;
- структуру проекта;
- naming conventions;
- уже существующие похожие экраны.

Если нужная страница уже существует — доработай ее.

Если существует route-заготовка — используй ее.

Если нужно создать новую страницу — выбери route, который логично следует из архитектуры и соглашений проекта.

Не создавай случайный `/figma`, `/test`, `/demo` или другой временный маршрут только ради демонстрации, если проект явно предполагает другое место.

После реализации открой именно конечную страницу приложения.

# 6. Переиспользуй существующие компоненты

Перед созданием нового компонента проверь, нет ли его уже в проекте.

Особенно проверь:

- Button;

Если существующий компонент визуально соответствует Figma и предназначен для этого случая — переиспользуй его.

Не создавай дубликаты компонентов без причины.

При этом не жертвуй визуальной точностью только ради формального переиспользования.

---

# 7. Ассеты получай самостоятельно

Все необходимые ассеты получи сам.

Используй доступные Figma/MCP tools для извлечения:

- SVG;
- icons;
- logos;
- illustrations;
- photos;
- images;
- backgrounds;
- exported layers.

Не проси меня скачивать их вручную.

Не используй:

- emoji вместо иконок;
- случайные иконки из другой библиотеки;
- placeholder images;
- приближенные SVG;
- CSS-рисунки вместо оригинального ассета;

если оригинал доступен из Figma.

Если в проекте уже лежит нужный ассет — используй существующий.

---

# 8. Шрифты

Определи используемые в Figma шрифты самостоятельно.

Затем проверь, есть ли они в проекте.

Используй:

- локальные font files;
- существующие `@font-face`;
- framework font loader;
- уже подключенный web font;
- существующую typography system.

Не заменяй шрифт на системный только потому, что это быстрее.

Шрифт критически влияет на:

- ширину текста;
- переносы;
- высоту строк;
- размеры блоков;
- визуальное совпадение.

Если конкретный шрифт технически недоступен, сначала проверь все доступные источники проекта и только затем используй максимально близкий fallback.

---

# 9. Используй точные значения из Figma

Не придумывай значения на глаз, если Figma сообщает точные.

Это относится к:

- width;
- height;
- min/max dimensions;
- padding;
- margin;
- gap;
- radius;
- font size;
- line-height;
- letter-spacing;
- border width;
- shadow;
- blur;
- opacity;
- colors;
- gradients;
- icon size;
- image size;
- positions.

Например, если Figma содержит:

```css
padding: 14px 22px;
gap: 13px;
border-radius: 11px;
font-size: 17px;
```

не заменяй это автоматически на:

```css
padding: 16px 24px;
gap: 12px;
border-radius: 12px;
font-size: 16px;
```

только потому, что такие значения кажутся более стандартными.

Не округляй значения ради удобства.

---

# 10. Design tokens и variables

Если Figma использует variables / tokens, сначала проверь, существуют ли их аналоги в проекте.

Предпочтение:

1. существующий token проекта, если он соответствует значению;
2. существующий CSS variable;
3. theme value;
4. точное значение из Figma.

Не создавай десятки новых токенов без необходимости.

Но и не подменяй точный цвет похожим существующим token'ом, если визуально значения различаются.

---

# 11. Layout должен соответствовать Figma

Воспроизводи layout, а не только отдельные элементы.

Проверь:

- общий размер страницы;
- контейнер;
- content width;
- центрирование;
- sidebar width;
- header height;
- sticky/fixed behavior;
- grid;
- columns;
- rows;
- alignment;
- spacing;
- text wrapping;
- overflow;
- scroll;
- crop;
- object-fit;
- stacking;
- z-index;
- clipping.

Выбирай CSS-модель, соответствующую структуре Figma:

- flex;
- grid;
- absolute positioning;
- fixed positioning;
- sticky;
- intrinsic sizing.

Не используй absolute positioning повсеместно, если Figma построена на Auto Layout.

Не превращай нормальный responsive layout в жесткий набор координат.

---

# 12. Responsive behavior

Определи responsive behavior из:

- Auto Layout;
- constraints;
- min/max sizes;
- fill/hug/fixed sizing;
- breakpoint frames;
- вариантов компонентов;
- существующего проекта.

Если Figma содержит несколько breakpoint-версий — учти их.

Если breakpoint явно не указан, не выдумывай десятки произвольных состояний.

Поведение должно логично следовать из доступных данных.

---

# 13. Не допускаются визуальные "приближения"

Не заменяй:

- оригинальную иконку похожей;
- SVG на Unicode;
- изображение на gradient;
- сложную тень на обычный box-shadow "примерно такой же";
- точный radius на ближайший token;
- реальный шрифт системным;
- настоящий layout упрощенной сеткой;

если исходное решение можно реализовать.

Не удаляй детали только потому, что они мелкие.

---

# 14. Не меняй содержимое без необходимости

Текст из Figma должен совпадать с Figma, если задача не требует иного.

Не:

- сокращай текст;
- переписывай copy;
- исправляй формулировки;
- меняй регистр;
- меняй знаки препинания;
- заменяй числа;
- добавляй собственные подписи.

Сохраняй содержимое максимально точно.

---

# 15. Реализуй функциональные состояния

Если Figma явно показывает:

- hover;
- active;
- selected;
- disabled;
- focus;
- expanded;
- collapsed;
- error;
- loading;
- empty state;

реализуй их, если они относятся к целевому интерфейсу.

Если элементы очевидно интерактивны, не оставляй их визуально кликабельными, но полностью сломанными, если функциональность можно определить из проекта.

Не придумывай бизнес-логику, которую невозможно вывести из существующего приложения или Figma.

---

# 16. Не останавливайся после первой реализации

Первая версия кода — только начало.

После реализации обязательно проведи собственную визуальную проверку.

Не пиши мне:

> "Готово, можете проверить."

Проверку выполняешь ты.

---

# 17. Обязательный цикл визуальной проверки

После первой реализации:

1. запусти проект;
2. дождись успешной сборки;
3. открой целевой route;
4. выставь viewport, соответствующий целевому Figma frame;
5. сделай screenshot результата;
6. получи reference screenshot из Figma;
7. сравни их;
8. найди отличия;
9. исправь код;
10. повтори screenshot;
11. снова сравни.

Цикл:

```text
inspect
→ implement
→ run
→ screenshot
→ compare
→ fix
→ screenshot
→ compare
→ fix
```

повторяй до тех пор, пока дальнейшие изменения не перестанут давать заметное улучшение.

---

# 18. Что обязательно сравнивать визуально

Во время каждого прохода проверь минимум:

### Геометрия

- x/y position;
- width;
- height;
- container sizes;
- page margins;
- alignment;
- centering;
- gaps;
- padding;
- grid;
- element order.

### Typography

- font;
- weight;
- size;
- line-height;
- letter-spacing;
- text width;
- wrapping;
- number of lines;
- vertical alignment.

### Controls

- button size;
- input size;
- icon placement;
- checkbox/radio geometry;
- selected states;
- disabled states.

### Visual effects

- colors;
- gradients;
- opacity;
- borders;
- radius;
- shadows;
- blur.

### Images

- exact asset;
- dimensions;
- crop;
- object-fit;
- object-position;
- clipping.

### Icons

- exact SVG;
- width;
- height;
- stroke/fill;
- alignment;
- distance from text.

---

# 19. Используй image diff, если доступен

Если доступен pixel diff / image comparison tool — используй его.

Сравнивай reference и browser screenshot не только глазами.

Если возможно, используй:

- overlay;
- difference image;
- pixel diff;
- bounding boxes;
- measurement tools.

При этом не оптимизируй слепо под антиалиасинг текста, если геометрия уже совпадает.

Главная цель — убрать реальные визуальные расхождения.

---

# 20. Проверяй font rendering отдельно

Если большая часть diff приходится на текст:

1. проверь, что загружен правильный font family;
2. проверь правильный weight;
3. проверь font-style;
4. проверь line-height;
5. проверь letter-spacing;
6. проверь ширину контейнера;
7. проверь browser font loading;
8. проверь, что fallback не подменил шрифт.

Не компенсируй неправильный шрифт случайными margin/padding.

---

# 21. Не маскируй ошибки хаками

Не исправляй каждое отличие бессистемными:

```css
left: 3px;
top: -2px;
margin-left: 5px;
transform: translateX(2px);
```

если причина находится выше в layout.

Сначала ищи первопричину:

- неправильный font;
- неправильный container width;
- неверный parent gap;
- неправильный padding;
- неверный flex alignment;
- неверный SVG viewBox;
- неправильный image crop.

Используй точечные offsets только там, где они действительно являются частью дизайна.

---

# 22. Не ломай остальной проект

После реализации проверь, что изменения:

- не ломают существующие routes;
- не ломают shared components;
- не меняют глобальные стили без необходимости;
- не вызывают regressions;
- не создают конфликтов типов;
- не ломают build.

Если меняешь shared component, проверь его другие использования.

---

# 23. Код должен быть нормальным production-кодом

Pixel-perfect не означает грязный код.

Не создавай:

- один гигантский компонент на тысячи строк;
- бессмысленные дубли;
- inline styles для каждого элемента без причины;
- огромное количество magic numbers, если проект уже имеет подходящую структуру;
- мертвый код;
- временные файлы;
- debug logging;
- screenshot-only hacks.

Разбивай код на компоненты там, где это соответствует структуре интерфейса и проекта.

---

# 24. Не делай ненужный рефакторинг

Не переписывай unrelated части проекта.

Не меняй архитектуру ради одной страницы.

Не обновляй зависимости без необходимости.

Не меняй форматирование сотен файлов.

Scope изменений должен быть минимальным и связанным с реализацией Figma.

---

# 25. Проверки перед завершением

Перед завершением обязательно проверь:

- приложение запускается;
- route работает;
- страница открывается без ошибок;
- нет console errors;
- нет broken assets;
- нет 404 для изображений/fonts;
- все необходимые SVG загружены;
- нет placeholder'ов;
- нет случайных fallback fonts;
- нет пропущенных слоев Figma;
- нет очевидных layout differences;
- responsive behavior не сломан.

Также запусти доступные в проекте проверки:

- lint;
- typecheck;
- tests;
- build;

если соответствующие scripts существуют.

---

# 26. Когда считать работу завершенной

Работа считается завершенной не тогда, когда страница "похожа" на Figma, а когда:

- структура соответствует макету;
- размеры соответствуют;
- spacing соответствует;
- typography соответствует;
- assets соответствуют;
- цвета соответствуют;
- основные состояния соответствуют;
- visual comparison выполнен;
- найденные расхождения исправлены;
- повторная проверка выполнена;
- проект успешно проходит доступные технические проверки.

Абсолютное равенство каждого пикселя может зависеть от browser rasterization и font antialiasing, поэтому ориентируйся на **отсутствие исправимых визуальных расхождений**.

---

# 27. Если что-то неоднозначно

Не задавай вопрос пользователю сразу.

Сначала попробуй определить ответ самостоятельно через:

1. Figma;
2. соседние frames;
3. component variants;
4. Code Connect;
5. проект;
6. router;
7. design system;
8. существующие страницы;
9. git history, если доступна и полезна;
10. browser/runtime behavior.

Задавай вопрос только если существует действительно критичная неоднозначность, которую невозможно надежно разрешить из доступных источников и которая блокирует корректную реализацию.

---

# 28. Приоритет источников

Для **визуального результата** используй следующий порядок:

1. целевой Figma frame;
2. Figma variables / component properties;
3. Figma assets;
4. связанные design-system компоненты;
5. существующий проект.

Для **архитектуры и интеграции в приложение**:

1. существующая архитектура проекта;
2. существующие routes;
3. существующие shared components;
4. design system;
5. Figma.

Иными словами:

- внешний вид должен соответствовать Figma;
- реализация должна естественно жить внутри текущего проекта.

---

# 29. Формат финального ответа

Когда все завершено, дай короткий отчет.

Укажи:

- какой route реализован;
- какие основные файлы изменены;
- какие новые файлы созданы;
- какие ассеты добавлены;
- какие проверки выполнены;
- выполнялся ли визуальный screenshot comparison;
- остались ли известные отличия.

Не пиши длинный пересказ процесса.

Если известных визуальных расхождений нет, так и укажи.

---

# 30. Начало работы

После получения Figma-ссылки:

1. исследуй Figma;
2. исследуй проект;
3. самостоятельно определи target frame;
4. самостоятельно определи viewport;
5. самостоятельно определи route;
6. найди/скачай необходимые assets;
7. реализуй интерфейс;
8. запусти приложение;
9. визуально сравни с Figma;
10. самостоятельно исправь отличия;
11. повтори проверку;
